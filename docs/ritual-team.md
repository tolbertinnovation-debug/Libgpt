# Ritual Coding's five-agent website team

A first prompt in a new Build starts a supervisor-led website project. The supervisor creates a shared implementation contract and assigns four specialists: design and SVG assets, HTML pages, JavaScript interactions, and content and supporting materials. The specialists run concurrently, with exclusive ownership of their assigned files. They generate complete files in batches of two. The existing server-side provider credentials and model routing power all five roles; these are distinct model calls with different responsibilities, rather than five visual progress labels on one response.

Every completed file fence is saved immediately. IndexedDB stores project files, messages, versions and team checkpoints; localStorage is a compatibility fallback. Storage errors stop approval and tell the user to download the files. Files save on the current device and browser, not to an unconfigured cloud account. Download All files for a complete ZIP, or use the existing backup feature to transfer projects and resume work elsewhere. The single-page download contains the home page; multi-page websites require the ZIP.

Stop cancels active provider requests and keeps completed files. Resume retains the original plan, skips completed files, checks the current output and runs a fresh supervisor review. Reloaded in-progress projects show a resume action. Restored backups retain the plan and require review again. Typed edits and fixes save automatically; edits to a supervised project also trigger a new supervisor review. Manual code edits or version restoration invalidate previous approval.

Approval requires all assigned files, valid structured output, local references and a supervisor source review. Every HTML page is opened in a sandbox at 390 px and 1280 px for startup errors, overflow, loaded resources, metadata, labels and section references. The supervisor compares actual HTML, CSS and JavaScript contracts against the brief and latest requested change. Known faults override a model's attempted approval. Up to three repair rounds send corrections back to the files' original owners, followed by fresh checks and review. Remaining defects stay visible and can be resumed; the UI never labels an incomplete or unsaved run approved.

The checks do not submit forms, make purchases or prove that every interactive flow works. Test buttons, form outcomes and external services before publishing. Backend services, authentication, payments, databases and integrations require real configuration and are not made operational by generating static HTML. The generated site and README must disclose these requirements. Browser previews route local page links and material downloads through project files, rather than navigating into Grandpa AI's hosting application. Programmatic navigation, query-dependent code and network APIs may still require a real hosting environment.

Plans support up to twelve HTML pages and up to twelve files per specialist, forty-eight assigned files total. These are explicit execution and review bounds, not a promise of unlimited compute. Existing rate, access, provider and response limits remain active. Projects larger than the available source review context stay unapproved rather than pretending all source was inspected. No GitHub OAuth setup is required to generate, edit, preview, save or download; GitHub publishing continues to require the existing deployment configuration.

Validation includes unit tests for parallel execution, file ownership, bounded repairs, no-op repair detection, cancellation, save ordering, quotas, interrupted reviews, backup recovery, safe paths and false approval rejection. Browser smoke tests use actual Express routes with a mocked provider, so they verify application behavior without claiming a live model quality evaluation.

Planning failures keep the original request and show the actual diagnostic above the recovery control. Retry planning, or type Continue, to restart the supervisor rather than editing an empty project. A malformed or invalid plan gets one bounded corrective generation attempt. Provider quota, access and availability failures are reported directly. Planning and update screens show a spinner and elapsed time; after failure, the spinner stops and recovery controls remain reachable in the scrollable conversation area. Website checks, AI connection checks, publishing and GitHub loading also show a loading indicator.
